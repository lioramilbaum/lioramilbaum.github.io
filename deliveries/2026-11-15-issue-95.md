# feat: generate delivery docs in a post-merge workflow

**PR:** [#106](https://github.com/lioramilbaum/lioramilbaum.github.io/pull/106) · **Opened:** 2026-11-15 · **Hackathon:** Day 9 of the Qodo Software Factory hackathon, [Set up quality gates](https://github.com/orgs/qodo-hackathon/discussions/11): Qodo's PR findings were worked through with Review Resolver under a saved quality gate (fix every valid High and Medium, report each Low to the owner), as the Qodo notes below record.

## Why

_From the PR description (author-written)._

Every merged PR here needs a delivery doc (AGENTS.md rule 6), and until now a person had to remember to run the delivery-doc skill after each merge. #93 merged with no doc until someone asked for one. The doc is generated from GitHub data and nothing in it is written by hand, so the remaining manual step was just running the generator and opening the docs PR. This PR moves that step into the factory.

## How

_From the PR description (author-written)._

- A new `Delivery doc` workflow runs on every push to `main`, and can be dispatched by hand with a PR number. It runs only on `lioramilbaum/lioramilbaum.github.io`, with read-only `GITHUB_TOKEN` permissions and no `pull_request_target`.
- All the logic is in `scripts/delivery-run.sh`, so it can be tested offline:
  1. It skips, and logs why, in four cases:
     - the delivery window has ended;
     - a direct push: after four lookups, the run checks the recently merged PRs for one whose merge commit is this commit, and then any PR the subject names. Only a commit that no merged PR claims is skipped, and a merge commit that no PR claims fails the run instead;
     - a Renovate PR;
     - a docs PR: every changed file is under `deliveries/`, read from git rather than the API's 100-file list.
  2. It waits up to 20 minutes for Qodo's review of the merged head to settle (`scripts/qodo-status.sh`). A review that is stale or missing keeps it waiting too, and if the review is still not settled at 20 minutes, the run fails.
  3. It reuses the one open docs PR (rebased onto `main`, still one commit) or starts `docs/delivery-pr-N`.
  4. It runs the existing generator unchanged, and requires `--check` to print `is current` and `scripts/check-delivery.sh` to pass before it pushes.
  5. It pushes to the fork and opens or updates the docs PR to upstream, assigned to the owner, then re-reads the PR to confirm it is open on the pushed commit.
- Every other outcome fails the run and names the reason (rule 11). A `qodo-open` of `unknown`, `none` or `other` fails: the generator then reads a review other than the one the status waited for, so nothing is committed. A count above 0 warns and adds a Limitations line, because the `qodo-findings` status, not the doc, is the merge gate (rule 9).
- Tokens: a PR opened with `GITHUB_TOKEN` triggers no other workflow, so CI would not check the docs PR. The workflow reuses the agent run's `AGENT_FORK_TOKEN` (push to the fork) and `AGENT_PR_TOKEN` (open and edit the PR), set on its one run step only. The script copies them into unexported shell variables and removes them from its environment, so none of the scripts, git commands or builds it runs inherits them, and the generator also runs both site builds with no read token in their environment. That is not isolation: code running as the same user could still read the tokens from `/proc`. Every script the run executes is code already merged to `main`, which could just as well change `delivery-run.sh` itself, so the trust boundary is the merge. git gets the fork token through an askpass script, never in a URL, an argv or a git config.
- Runs queue one at a time on the job's concurrency group (`cancel-in-progress: false`, `queue: max`), so two close merges land in one docs PR and none is dropped (the #76 and #90 lesson).
- Screenshots: the generator's preview server now takes `SERVE_HOST` (`127.0.0.1` by default, or `0.0.0.0`), and the workflow sets `0.0.0.0` so the screenshot container on the Ubuntu runner can reach it through host-gateway.

## Limitations

_From the PR description (author-written)._

- CI cannot run the workflow end to end: real GitHub, the real tokens and a real Docker screenshot. The merge of this PR is the first real run. It should open `docs/delivery-pr-<this PR>`, and `Check site` should run on that docs PR.
- The screenshot step on the Ubuntu runner is not tested in CI. CI's Snapshot script test shows host-gateway reaches a `0.0.0.0` server on ubuntu-26.04, and a test checks that the generator binds the address it is given. The first real run that changes the homepage is the check, and a failure there turns the run red.
- When the commit-to-PR lookup finds no merged PR, the run tries it up to four times, 30 seconds apart. Then:
  - It lists the 50 most recently updated PRs merged into `main`, through GraphQL, and continues with the one whose merge commit is the push's commit.
  - If none matches and the subject names a PR (`Merge pull request #N`, or a trailing `(#N)`), the run reads that PR directly. If it is merged with this commit, the run continues with it; otherwise it skips the push.
  - A merge commit that no PR claims fails, and names the manual dispatch that recovers it (`gh workflow run "Delivery doc" -f pr=N`).
  - A single-parent commit that no PR claims is skipped as a direct push, and the log says so.
  - A merge older than the 50 most recent merged PRs, with the commit lookup still empty, is skipped the same way, and a dispatch recovers it.
- About 35 of the script's `die` lines have no test case. They fire only when git, jq or the generator fails on input the run has just read or produced, or they can't be reached because an earlier check already caught the case. Every die line that a PR's own data or a GitHub response can reach has a case.
- The two tokens are removed from the script's environment before it runs any script, git command or build, so none of them inherits them (its first lines, the cd through dirname, run before the removal and see the tokens). This is not isolation:
  - The script's own initial environment still holds them.
  - Code running as the same user could read them from `/proc`.
  - Every script the run executes is code already merged to `main`. That code is trusted as much as `delivery-run.sh` itself, since a merged change could change any of them.
- Reusing an open docs PR fetches its branch from the fork without a token. That works while the fork is public; a private fork fails the run, red, naming the fetch.
- When a reused docs PR's doc comes out unchanged, nothing is pushed, so the docs PR's base is not refreshed. The run logs this, and still rewrites the docs PR's title and body.

- When the commit-to-PR lookup finds no merged PR, the run tries it up to four times, 30 seconds apart. Then:
  - It lists the 50 most recently updated PRs merged into `main`, through GraphQL, and continues with the one whose merge commit is the push's commit.
  - If none matches and the subject names a PR (`Merge pull request #N`, or a trailing `(#N)`), the run reads that PR directly. If it is merged with this commit, the run continues with it; otherwise it skips the push.
  - A merge commit that no PR claims fails, and names the manual dispatch that recovers it (`gh workflow run "Delivery doc" -f pr=N`).
  - A single-parent commit that no PR claims is skipped as a direct push, and the log says so.
