# feat: remove the agent run's labels when an issue closes

**PR:** [#138](https://github.com/lioramilbaum/lioramilbaum.github.io/pull/138) · **Opened:** 2026-11-24 · **Hackathon:** [Day 14: Turn your quality gate into a workflow](https://github.com/orgs/qodo-hackathon/discussions/16): this is the PR inside the guarded path (`.github/**`). It adds a workflow, so it stays for a person to review even when Qodo's review is clean.

## Why

_From the PR description (author-written)._

Issue #64: the agent run marks an issue with one of four labels (`ready-for-agent`, `agent-working`, `agent-stuck`, `agent-done`). Nothing removed them when the issue closed, so a closed issue kept a label that describes a run in progress or a run that stopped. Issue #48 is closed and still shows `agent-stuck`. The labels are how the owner sees what the agent is doing, so a stale one is a wrong status.

## How

_From the PR description (author-written)._

- A new workflow runs when an issue closes and removes whichever of the four labels the issue carries. It leaves every other label.
- The removal is a small script, not inline workflow text, so the agent runner's existing offline tests can run it with a stub in place of `gh` (AGENTS.md rule 8).
- The script reads the issue's labels first and removes only the ones present, so a label that is absent cannot fail the run. If it cannot read the labels it fails, and if there is nothing to remove it says it skipped and why (AGENTS.md rule 11).
- The job uses `GITHUB_TOKEN` with `issues: write` and nothing else. It needs no new secret. A label removed with `GITHUB_TOKEN` starts no other workflow, and `agent-run.yml` runs only on `labeled`.
- The cleanup runs once, at the close. A run that is still active when its issue closes would add `agent-stuck` or `agent-done` afterwards, so the runner now reads the issue's state right before it adds either label, and skips the label when the issue is closed. If it cannot read the state it adds the label as before and warns: an open issue that silently lost `agent-stuck` would hide a stopped run (AGENTS.md rule 11).
- `scripts/check-workflows.sh` pins the new workflow as it pins the agent run and the Delivery doc workflow: a change to its trigger, guard, permissions or steps fails CI.

## What

_From the PR description (author-written)._

- `.github/workflows/agent-labels.yml` (new, "Agent labels"): on `issues: closed`; one job, guarded to this repository and to issues that are not pull requests; `ubuntu-26.04`, 5-minute timeout; checkout of main at the pinned SHA with `persist-credentials: false`, then `bash scripts/agent-labels.sh --issue "$ISSUE"`, with the issue number and the token passed through `env:`.
- `scripts/agent-labels.sh` (new): takes `--issue N` (a positive integer), reads the labels with `gh issue view`, and removes the agent labels present with one `gh issue edit`. It prints `removed:`, `skipped:` or `error:`, and exits 1 on an error.
- `scripts/check-workflows.sh`: fails if `agent-labels.yml` is missing, and pins its trigger, permissions, single job, guard, runner, timeout, its two steps with their keys, run text and env, no `secrets.`, no expression inside `run:`, and a SHA-pinned `uses:`.
- `scripts/agent-run.sh`: a helper, `status_label_ok`, used at the two places that add a status label to the issue (`agent-stuck` when a run stops, `agent-done` when it is ready). It prints `skipped: issue #N is closed, so <label> is not added`, or a warning when the state cannot be read. The label removals are unchanged.
- `scripts/test-agent.sh`: five more cases for the runner: an issue that closes during the run gets no `agent-stuck` and no `agent-done`, and an unreadable or unknown state adds the label with the warning.
- `scripts/test-agent.sh`: eight `labels:` cases. They cover a partial set of labels, all four with decoy labels that contain an agent label's text (`agent-done-old`, `needs agent-stuck`), decoys only, none of the four, a failed read, a failed removal, the usage errors, and issue numbers that are not positive integers (`abc`, `0`, `007`, `-5`). The `gh` stub also logs each argument on its own line, so a label with a space is one field.
- `AGENTS.md`: Setup says the four labels are removed when the issue closes, and that a run which stops or finishes after its issue closed adds no status label; rule 5 names the new pins; rule 8 lists the new script with its test; the Verify comments mention both.

## Limitations

_From the PR description (author-written)._

- CI cannot run the workflow itself: the `issues: closed` event and the job's `if:` only run on GitHub, from main, after this merges. `scripts/check-workflows.sh` pins their text, and the script the job runs is tested offline. The first issue closed after the merge is the check.
- The job checks out main with a token whose only permission is `issues: write`. That is expected to work because the repository is public, but no CI run proves it before the merge. If the first real run's checkout fails, the fix changes this issue's fifth criterion, so it is the owner's decision.
- A close in the moment between the runner's state check and its label write can still leave `agent-stuck` or `agent-done` on the closed issue. The owner removes it, or closes the issue again.
- `agent-working` is added at intake, right after the runner checks that the issue is open, and is removed when the run stops or finishes. A run that is killed before either leaves it; this PR does not change that.
- Issues that were already closed, such as #48, are not cleaned up: the workflow runs only when an issue closes.
- Red CI run (AGENTS.md rule 8): [run 45417970260](https://github.com/lioramilbaum/lioramilbaum.github.io/actions/runs/45417970260) on the deliberately broken revision a714071 (this PR, with `contents: read` added to the new workflow's permissions) failed at "Check workflow files", with this error annotated on `.github/workflows/agent-labels.yml`: `top-level permissions are not exactly issues: write`.
