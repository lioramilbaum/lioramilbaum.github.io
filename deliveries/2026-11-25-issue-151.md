# ci: run the Pages deploy upstream only, with least-privilege permissions

**PR:** [#152](https://github.com/lioramilbaum/lioramilbaum.github.io/pull/152) · **Opened:** 2026-11-25 · **Hackathon:** [Day 16: Scan your repo with Arnica](https://github.com/orgs/qodo-hackathon/discussions/18): the optional fix for two of the three findings Arnica reported on `main`, plus the missing repository guard found while fixing them.

## Why

_From the PR description (author-written)._

Arnica scanned `main` at e14cca2 on 2026-11-25 and reported three Medium findings, all in workflow files. Two are in the workflow that deploys the site, and both are real:

- "Excessive workflow permission assignment": `pages: write` and `id-token: write` were set for the whole workflow, so the `package` job, which only builds the site, could also deploy it and request an OIDC token. Only the `deploy` job needs either. AGENTS.md rule 5 says permissions stay least-privilege, and this workflow predates the rule's check.
- "GitHub actions artipacked vulnerability": the `package` job's checkout left the job token in `.git/config`, where every later step in the job could read it. It was not exploitable here: the artifact upload excludes `.git` and all dotfiles, and `https://lioramilbaum.com/.git/config` returns 404. The fix is one line, and the repo's newer workflows already have it.

Working on those two showed a third problem that Arnica did not report. The deploy workflow had no repository guard, so the owner's fork ran it on every push to its `main` (47 runs) and published a copy of the site. The other four guarded workflows already run in the upstream repository only.

Arnica's third finding, "Dangerous workflow triggers" on `qodo-findings.yml`'s `pull_request_target`, is not changed here. That trigger is deliberate (rule 5), and `scripts/check-workflows.sh` already pins that the workflow checks out main only and never runs PR code.

## How

_From the PR description (author-written)._

- The two write permissions move from the workflow level to the `deploy` job. The workflow level keeps `contents: read`, so a job added later starts with read-only access.
- The `package` job gets `contents: read` and `pages: read`. It needs the second one: its Configure Pages step calls `GET /repos/{owner}/{repo}/pages` and fails the job if that call is refused. This was read from the action's source at its pinned SHA, not assumed.
- The `deploy` job gets exactly `pages: write` and `id-token: write`, which is what `actions/deploy-pages` documents as its minimum. It has no checkout, so it needs no `contents` permission.
- The `package` job's checkout sets `persist-credentials: false`. No later step in the job runs git against the remote.
- Both jobs get `if: github.repository == 'lioramilbaum/lioramilbaum.github.io'`. In a fork the run still starts, and both jobs are skipped, so nothing is built or published there.
- `scripts/check-workflows.sh` pins all of it with exact comparisons, so a missing block, an extra scope, `write-all`, a renamed or added job, a second checkout, or a missing or widened guard fails CI with a message that names the problem. A missing `deploy-pages.yml` fails too (AGENTS.md rule 11).

## What

_From the PR description (author-written)._

- `.github/workflows/deploy-pages.yml`: both jobs are guarded to the upstream repository; workflow-level `permissions` is `contents: read` only; `package` has `contents: read` and `pages: read`, and its checkout has `persist-credentials: false`; `deploy` has `pages: write` and `id-token: write`. Triggers, schedule, concurrency, runner, environment and every `uses:` pin are unchanged.
- `scripts/check-workflows.sh`: fails if `deploy-pages.yml` is missing, and pins its workflow-level permissions, its two job names, each job's guard and permissions, and exactly one `actions/checkout` step in `package` with `persist-credentials: false`. The existing schedule, push and `workflow_dispatch` checks still run after the new ones.
- `AGENTS.md`: the Verify comment and rule 5 name the new pins.

## Limitations

_From the PR description (author-written)._

- CI cannot run the deploy workflow: it runs only from `main`, after the merge. `scripts/check-workflows.sh` pins the new text, and the first deploy after the merge is the check (criterion 5). If it fails, the live site stays as it is until a follow-up.
- The new permissions were tested once before the guard was added: the workflow was dispatched on the owner's fork from this branch ([run 45570618429](https://github.com/lmilbaum/lioramilbaum.github.io/actions/runs/45570618429), revision 8b10dce). `package` passed with `Contents: read`, `Metadata: read` and `Pages: read`, its Configure Pages step included. `deploy` was refused by the fork's `github-pages` environment, which allows `main` only, so nothing was published and the `deploy` job's own permissions were not exercised. With the guard, the same dispatch skips both jobs, so this test cannot be repeated on the fork.
- The guard itself is not exercised before the merge: CI pins its text, and criterion 8 checks it on the fork's next push to `main`. The guard does not stop the run from appearing in a fork (its jobs are skipped), and it does not remove the copy the fork already published; that is a setting on the fork.
- Red CI run for the permissions and the checkout (AGENTS.md rule 8): [run 45569474358](https://github.com/lioramilbaum/lioramilbaum.github.io/actions/runs/45569474358) on the deliberately broken revision 4e28642 (this PR's check and docs, with main's unchanged `deploy-pages.yml`) failed at "Check workflow files", with four errors annotated on `.github/workflows/deploy-pages.yml`: `top-level permissions are not exactly contents: read; pages: write and id-token: write belong on the deploy job only (issue #151)`; `job package permissions are not exactly contents: read and pages: read; it must not write (issue #151)`; `job package checkout does not set persist-credentials: false; the job token stays in .git/config for the later steps (issue #151)`; `job deploy permissions are not exactly pages: write and id-token: write (issue #151)`.
- Red CI run for the guard (AGENTS.md rule 8): [run 45573898419](https://github.com/lioramilbaum/lioramilbaum.github.io/actions/runs/45573898419) on the deliberately broken revision 7a9a970 (this PR without the two `if:` lines) failed at "Check workflow files", with two errors annotated on `.github/workflows/deploy-pages.yml`: `job package if is not exactly github.repository == 'lioramilbaum/lioramilbaum.github.io'; the deploy runs in the upstream repository only, so a fork never publishes a copy (issue #151)`; `job deploy if is not exactly github.repository == 'lioramilbaum/lioramilbaum.github.io'; the deploy runs in the upstream repository only, so a fork never publishes a copy (issue #151)`.
- `scripts/check-workflows.sh` reads YAML the way Ruby does, so `persist-credentials: no` passes the check although GitHub reads `no` as a string and the checkout step then fails at run time. The check on `agent-labels.yml` has the same gap. It fails loudly on GitHub, so it is left as it is.
- Arnica's re-scan (criterion 6) happens outside CI, after the merge.
