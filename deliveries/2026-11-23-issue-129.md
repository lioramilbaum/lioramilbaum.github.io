# feat: add a skill for updating the LinkedIn followers count

**PR:** [#130](https://github.com/lioramilbaum/lioramilbaum.github.io/pull/130) · **Opened:** 2026-11-23 · **Hackathon:** [Day 13: Teach your factory a new skill](https://github.com/orgs/qodo-hackathon/discussions/15).

## Why

_From the PR description (author-written)._

The homepage shows `N LinkedIn followers · as of <date>` from `_data/linkedin.yml` (AGENTS.md rule 3), and the owner updates it by hand. Each update is the same small procedure: check the value against the file's rules, build, run the checks, and confirm that the rendered line is the number that was given. Skip a step and an invalid value hides the line and turns CI red, or the page shows a number nobody wrote (issue #124). This PR writes that procedure as a project skill, so any session runs it the same way, during the hackathon and after it. It is the Day 13 challenge, "Teach your factory a new skill".

## How

_From the PR description (author-written)._

- A Claude Code project skill in the [Agent Skills format](https://agentskills.io/specification): `.claude/skills/update-linkedin-followers/SKILL.md`, with frontmatter `name` (matching the directory) and a `description` that says when it applies.
- The procedure uses the repo's existing scripts only, so the skill adds no code that needs its own tests (AGENTS.md rule 8). Its one check of the inputs is an inline `python3 -c` command that rejects an invalid value and prints the line the site must render.
- It compares output with input, not just that the line exists: the rendered `<p class="followers">` line in `_site/index.html` must match the expected line byte for byte (`cmp`).
- It proves that the check can fail: it builds a throwaway copy outside the repo with `followers: 012`, which YAML reads as octal 10, and expects the line hidden and `check-site.sh` to fail with its exact followers message. The real file is left untouched.
- It reports problems, it does not repair them: it never edits the layout or the checks to make a check pass. Ten stop conditions say when it must stop and ask, starting with "no count". LinkedIn has no source the agent may read, so the count always comes from the owner. The skill sets the as-of date itself, to the day of the update (`date +%F`), unless the owner names another date.
- Locale-proof: the expected date uses a fixed English month list and the output is written as UTF-8, so the comparison holds under any `LC_ALL`.

## What

_From the PR description (author-written)._

- `.claude/skills/update-linkedin-followers/SKILL.md` (new): the inputs, the format rules, the stop conditions, seven ordered steps with exact commands and the expected output of each (the last opens the PR), and the evidence to report.
- `AGENTS.md`: rule 3's followers sentence names the skill.
- Nothing is published: `_config.yml` already excludes `.claude/`, and `scripts/check-site.sh` already fails if `.claude` reaches `_site`.

_From the PR description (author-written)._

- Invalid input can run shell commands; Existing scratchpad files can be deleted (both Medium, raised on d0a13fa): fixed in 9ef280c. The owner's count and date are written to files and checked before any command; step 5 makes its copy with `mktemp -d` and removes only that directory. Cleared by Qodo on its re-review of 9ef280c; none was dismissed or marked by hand.
- Updates can push to the wrong repository (Medium, raised on 3201c76): step 2 checked that `upstream` exists, but not that `origin`, which receives the push, is the fork. Fixed in d78938e: step 2 and step 7 check that `origin`'s push URL is the lmilbaum fork, and step 2 that `upstream` is lioramilbaum/lioramilbaum.github.io. Qodo's re-review of d78938e no longer lists it.
- Updates can push to an unintended repository (High, raised on d78938e): that check read only the first push URL of `origin`, and `git push` sends to every push URL. Fixed in f6fda08: both checks read every push URL (`git remote get-url --push --all origin`) and stop unless there is exactly one and it is the fork. Qodo's re-review of f6fda08 no longer lists it.
- Skill ships before its fresh-session run is evidenced (Medium, raised on 3201c76 and still listed on f6fda08): the evidence is the comment on #129 at https://github.com/lioramilbaum/lioramilbaum.github.io/issues/129#issuecomment-7132102610. No file changed, so there was no push for Qodo to re-review, and the finding was marked implemented by hand with the owner's approval.

## Limitations

_From the PR description (author-written)._

- CI does not run the skill: no model call runs in CI, and `SKILL.md` is instructions to the model, not code under rule 8. #129's criteria 4 and 5 were checked by two fresh Claude Code sessions: the first ran the skill at 9ef280c (its update merged as #132), and after its five gaps were fixed, the second ran it at f6fda08 (its update merged as #135). The excerpts and the before and after text are in the comment on #129 at https://github.com/lioramilbaum/lioramilbaum.github.io/issues/129#issuecomment-7132102610. The second session was started with a count, so the no-count stop is evidenced by the first session only; the text that governs that case is the same at both commits. The `_data/linkedin.yml` update in #131 was made with an earlier draft of the skill and is neither run.
- The expected line repeats the profile link (`https://linkedin.com/in/lmilbaum`) that the layout and `check-site.sh` also hold. If the link changes, the skill's comparison stops at stop condition 5 until the skill is updated too.
