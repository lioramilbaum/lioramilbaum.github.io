# fix: sync the fork's main before pushing the delivery docs branch

**PR:** [#113](https://github.com/lioramilbaum/lioramilbaum.github.io/pull/113) · **Opened:** 2026-11-15 · **Hackathon:** Day 9 of the Qodo Software Factory hackathon, [Set up quality gates](https://github.com/orgs/qodo-hackathon/discussions/11): a fix found by the first real run of the Delivery doc workflow built under Day 9's gate (#106).

## Why

_From the PR description (author-written)._

The Delivery doc workflow's first real run, for PR #106, generated a current doc, and then GitHub refused to push the docs branch to the fork: `refusing to allow a Personal Access Token to create or update workflow .github/workflows/delivery-doc.yml without workflow scope`. The fork's `main` was behind upstream's, and the docs branch is based on upstream's `main`, so the push carried a workflow file the fork didn't have. The fork's `main` falls behind after every merge, so every run would hit this until someone synced it by hand. Separately, a Renovate merge to `main` started the job only for the script to skip it.

## How

_From the PR description (author-written)._

- Before the docs branch is pushed, `scripts/delivery-run.sh` makes the fork's `main` equal to upstream's. It reads both mains with git, with no token, and handles four cases:
  - **Equal:** it logs that the fork is current and writes nothing.
  - **Diverged** (the fork's `main` has commits upstream lacks): the run fails, naming both SHAs and the number of commits, and pushes nothing.
  - **Behind:** it pushes upstream's SHA to the fork's `main` with a plain git push, made with `AGENT_FORK_TOKEN` through git's askpass only. GitHub accepts that push only as a fast-forward; the run never forces it and takes no lease (a lease allows a non-fast-forward update when it matches). It then reads the fork's `main` again and requires it to equal upstream's SHA, and logs both SHAs.
  - **Refused, or not upstream's afterwards:** the run fails with git's message, and nothing is pushed.
- The sync runs only on the push path, after every skip, so a skipped run makes no write.
- The token that makes the push is the fork token the run already had, `AGENT_FORK_TOKEN`. It now also has the fine-grained Workflows read and write permission on the fork, because GitHub refuses a token push that adds or changes `.github/workflows/` files without it (the #106 run: `refusing to allow a Personal Access Token to create or update workflow .github/workflows/delivery-doc.yml without workflow scope`). The permission lets a push from the agent run write workflow files on the fork too; AGENTS.md residual risk 10 records that.
- The Delivery doc workflow's `if:` now also requires `github.actor != 'renovate[bot]'`, so a Renovate automerge does not start it. Renovate merges by pushing to `main` itself (`platformAutomerge` is false); the push run for its merge of #105 (`5817b6a`) has actor `renovate[bot]`. A manual dispatch still runs, and a dispatched Renovate PR is still skipped by the script, with the reason logged.

## What

_From the PR description (author-written)._

- `scripts/delivery-run.sh`: `push_fork_main` (the plain push, with the fork token on askpass only), `sync_fork_main` (the four cases above), and the push block, which runs the sync right before the docs-branch push.
- `.github/workflows/delivery-doc.yml`: the comments describe the sync, and the job's `if:` has the actor term. The run step's env is unchanged.
- `scripts/check-workflows.sh`: pins the new `if:`. The env and the `secrets.` count stay as they were.
- `scripts/test-delivery.sh`: a fixture fork whose `main` can be refused (a pre-receive hook) or rewound after an accepted push (a post-receive hook), and a one-shot hook that moves a ref between the run's read and its main push. The cases cover:
  - behind, for a new and for a reused docs PR;
  - equal;
  - diverged;
  - a refused push;
  - a fork `main` that moves before the push, which stays red with the moved commit kept and no merge commit;
  - a mismatch on the re-read;
  - a fork with no `main`;
  - upstream gaining a commit after the read.

  dr32 checks that the fork token answers both pushes. The skip cases run with the fork behind, to show that a skip pushes nothing.
- `AGENTS.md`: Setup (the sync, the Workflows permission, the Renovate skip), residual risk 10, the Tokens and Backstop bullets, and rule 6.
- `.claude/skills/delivery-doc/SKILL.md`: B4 hands a refused main push, or a moved or diverged fork `main`, to the owner, with no re-dispatch.

A first design used GitHub's merge-upstream API. ## Limitations

_From the PR description (author-written)._

- CI cannot run the real push: a real fork, a real token and GitHub's receive side. The fixture fork is a local bare repo, and its refusal and rewind are hooks that stand in for GitHub. The first real run after this merge is the check. This PR changes `delivery-doc.yml`, so the fork is behind by a workflow commit, and the real push will need the Workflows permission on `AGENT_FORK_TOKEN`.
- `AGENT_FORK_TOKEN` must have the Workflows permission before the merge. Without it, the first run that has a workflow commit to sync fails at the push, red, with GitHub's message in the log; the owner adds the permission and re-dispatches.
- If the run fails after a successful main push (for example, the docs-branch push fails), the fork's `main` is left at upstream's SHA with nothing pushed. That is harmless: it is a fast-forward, and the next run finds the fork current.
- The fork is read without a token, which works while it is public; a private fork fails the run, red, naming the fetch.
