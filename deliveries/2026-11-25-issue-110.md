# fix: keep a reused docs PR's notes and skip an empty docs PR

**PR:** [#161](https://github.com/lioramilbaum/lioramilbaum.github.io/pull/161) · **Opened:** 2026-11-25

## Why

_From the PR description (author-written)._

Issue #110 collects what Qodo's last review of #106 (the Delivery doc workflow) left open. Two of the findings are bugs in a workflow that runs on every merge to `main`:

- **An empty docs PR blocked new docs.** The run reuses the one open docs PR. Its filter asked whether every changed file is under `deliveries/`, which is also true of a PR with no changed files at all. A docs PR whose changes `main` had already absorbed was picked for reuse, and the run then failed.
- **The owner's notes on a docs PR were wiped.** When the run adds a doc to an open docs PR it rebuilds the PR description and keeps the `## Hackathon` and `## Qodo notes` sections. A description edited in GitHub's web UI has CRLF line endings, so neither heading matched, and the rebuilt description replaced the owner's text with two empty sections.

The other two are instructions in AGENTS.md rule 6 that did not work as written: the doc check failed on a fresh clone after a squash merge, and the run lookup read a list by position.

## How

_From the PR description (author-written)._

- The reuse filter requires at least one changed file. An empty docs PR is ignored, and the run opens a new docs PR.
- Line endings are stripped before the headings are matched, so a CRLF description keeps both sections, and the rebuilt description has no `\r`.
- A description with a heading the run cannot read, such as `### Hackathon` above any `## Hackathon`, fails the run instead of being overwritten (rule 11). The description is read once before the push, so that failure pushes nothing.
- The description is read again just before it is edited, and the kept sections come from that second read. Generating a doc takes minutes, and without the second read an edit the owner made in that time would be overwritten by the earlier copy. If the second read fails, or finds an unreadable heading, the run fails and says the branch is pushed and the description is not edited.
- Rule 6's check step now fetches the code PR's head (`git fetch upstream main pull/N/head`): after a squash or rebase merge that commit is not in `main`'s history, so a fresh clone lacks it.
- Rule 6's run lookup filters by the merge commit (`gh run list --event push --commit SHA`), or by the dispatch's `pr` input, never by a run's place in the list.

## What

_From the PR description (author-written)._

- `scripts/delivery-run.sh`: the reuse filter; two helpers, `body_tail` and `unreadable_heading`, that hold the two matches once each; the early read and the late read of a reused PR's description, with their three failure messages.
- `scripts/test-delivery.sh`: six new cases, and one stricter one.
  - `dr91`: an empty docs PR is not reused, and a new docs PR is opened.
  - `dr92`: a reused docs PR with a CRLF description keeps its Hackathon and Qodo notes text.
  - `dr93`: an unreadable heading fails the run before the push, naming the heading.
  - `dr94`: the description changes between the two reads, and the second read's text is kept.
  - `dr95`: the second read fails. The run fails with that reason, and no description is written.
  - `dr96`: the second read has an unreadable heading. The run fails naming it, and no description is written.
  - `dr65` (existing): now also asserts that nothing was pushed when the first read fails.
- `AGENTS.md`: two sentences in rule 6, the check step and the run lookup.

With the `scripts/delivery-run.sh` from `main`, `dr91` to `dr96` and the stricter `dr65` fail and every other case passes. With only the second read removed, exactly `dr94`, `dr95` and `dr96` fail.

## Limitations

_From the PR description (author-written)._

- A description with no `## Hackathon` or `## Qodo notes` heading at all (for example `**Hackathon**` as bold text) still gets two empty sections, as before this change. The new failure covers a heading-like line the run cannot read, which is what #110 asks for. The description the workflow itself writes always has both headings.
- The unreadable-heading check is a prefix match on lines above the first heading the run can read. A line such as `## Hackathon day plan` there fails the run. It fails safe: nothing is overwritten.
- Everything after the first kept heading is kept, including any later `##` section. This is unchanged.
- The tests use a stub in place of `gh`. The real reads and the real edit of a docs PR's description run only in the Delivery doc workflow, from `main`, so they run for the first time on the first reused docs PR after this merges.
- The two AGENTS.md commands are instructions for a person or an agent, not code CI runs. The run lookup was tried once by hand against `main`'s latest push run and returned that run.
- An edit made in the moment between the second read and the edit call can still be lost. Only building the description, which is local, happens in between.
