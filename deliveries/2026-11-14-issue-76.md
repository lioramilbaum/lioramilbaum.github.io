# fix: queue qodo-findings runs instead of cancelling them

**PR:** [#101](https://github.com/lioramilbaum/lioramilbaum.github.io/pull/101) · **Opened:** 2026-11-14 · **Hackathon:** Day 8 of the Qodo Software Factory hackathon, [Review before you commit](https://github.com/orgs/qodo-hackathon/discussions/10): this change was reviewed by Qodo's local review while still uncommitted (tracking issue #100).

## Why

_From the PR description (author-written)._

The `qodo-findings` gate kept leaving PRs with a red `post-status` check even when nothing was wrong.
- A push starts the Qodo findings workflow on `pull_request_target`, and seconds later Qodo edits its review comment, which starts `issue_comment` runs of the same workflow.
- The concurrency group had `cancel-in-progress: true`, so the comment run cancelled the push run.
- GitHub doesn't attach `issue_comment` runs to the PR head, so the cancelled run was the only `post-status` the head showed. The merge state went `UNSTABLE`, and the agent runner treats a cancelled check as a failure.

It happened on PRs #75, #97, #98 and #99 (for example, runs 43624069078 and 43635565731).

## How

_From the PR description (author-written)._

- **Queue, don't cancel.** The `post-status` job keeps one concurrency group per PR, but with `cancel-in-progress: false` and `queue: max`. Runs for one PR go one at a time, in the order they started waiting (up to 100 pending), and none is cancelled.
  - Ordering stays correct without cancelling. `scripts/qodo-gate.sh` keeps no state between runs and re-reads the PR head and Qodo's review before every post, so the last run to execute posts the latest state.
  - A run in the 5-minute settle loop leaves within about 30 s of a push (the head goes stale).
- **Two alternatives rejected.**
  - An expression for `cancel-in-progress` (true except on `pull_request_target`) still cancels, because the incoming comment run's `true` decides it.
  - Separate groups per event let two runs post at once. A comment run still settling could then overwrite a "Draft" pending.
- **Only Qodo's comments run the job.** Before this PR's first commit, Qodo's local review of the uncommitted change pointed out that with queueing, every comment by anyone would queue a full run ahead of the one that matters. The job's `if:` now runs `issue_comment` events only for comments by `qodo-code-review` or `qodo-code-review[bot]`. Those are the logins `qodo-status.sh`, `generate-delivery.sh` and `agent-run.sh` read as Qodo's review, and no other comment can change the gate's answer. The concurrency sits on the job, not the workflow. A run started by anyone else's comment has its job skipped by the `if:` before the job's concurrency applies, so it never joins the queue and can't fill it.
- **`scripts/check-workflows.sh` pins it** (rule 8):
  - there must be no workflow-level concurrency, and the job's block must be exactly `group`, `cancel-in-progress: false` and `queue: max`;
  - the job's `if:` must be exactly the guarded string;
  - each of the three scripts must carry exactly the same login pair, followed directly by its `and`, on a live, uncommented line, read through new read-only mounts, so the allowlist can't drift or widen.
- **AGENTS.md** rule 9 and the Verify line describe the queueing and the comment filter.

**Red CI run (rule 8).** The first push was the new `check-workflows.sh` against the old `qodo-findings.yml`, with `qodo-status.sh`'s select deliberately moved into a comment. All three new assertions failed: ([run](https://github.com/lioramilbaum/lioramilbaum.github.io/actions/runs/43641045769), commit 73d8df3). The second push is the change itself: ([run](https://github.com/lioramilbaum/lioramilbaum.github.io/actions/runs/43641139600), commit 8716b4d).

- **Extra review authors pass validation** (`scripts/check-workflows.sh`). It was valid: the cross-check matched the login pair as a substring, so an appended `or .author.login == "x"` still passed. - **Comment floods cancel PR head checks** (`.github/workflows/qodo-findings.yml`). It was valid: with workflow-level concurrency, every comment's run joined the queue before the job's `if:` skipped it, and GitHub cancels runs beyond 100 pending. Fixed: the concurrency moved onto the `post-status` job, and `check-workflows.sh` forbids a workflow-level block.

Qodo's review of 77b5daf, the head, added no finding. It re-attributed the comment-flood fix as implemented, and it still listed the authors finding against 8716b4d, so that one was marked implemented once its fix was confirmed on the head (`scripts/check-workflows.sh:84`).

## Limitations

_From the PR description (author-written)._

- **The real scheduling can't run in CI** (criterion 1). Both the `pull_request_target` and `issue_comment` triggers run main's copy of the workflow, so this PR's own checks still use the old block. The job's `if:` also skips every run outside the upstream repository. It will be confirmed on the first PR after the merge (usually the delivery-doc docs PR), from these three:
  - the run list shows `issue_comment` runs queued after the `pull_request_target` run, with none cancelled;
  - `post-status` passes on the head;
  - the merge state is not `UNSTABLE`.

  The evidence goes on #76 as a comment.
- **The job's `if:` keeps other comments out of the queue, but the docs don't say so.** GitHub's docs say "up to 100 jobs or workflow runs can be pending", so `queue: max` applies to job-level concurrency. They don't say that a job skipped by its `if:` never joins its group. That is the assumption the design rests on, and it is confirmed after the merge with the rest of criterion 1.
- **`queue: max` is from GitHub's 2026-05-07 changelog.** If GitHub rejected the key, the first run after the merge would show "Invalid workflow file", and the change can be reverted at once.
- **A queued run can wait up to about 6 minutes** behind a run that is waiting for Qodo's review to settle. Waiting in the queue doesn't count toward the job's 10-minute timeout.
