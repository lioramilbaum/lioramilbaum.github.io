# feat: Create each PR's delivery doc after the PR merges, in a separate PR

**PR:** [#60](https://github.com/lioramilbaum/lioramilbaum.github.io/pull/60) · **Opened:** 2026-11-09

## Why

_From the PR description (author-written)._

Every PR used to carry its own delivery doc, generated into the PR's single commit after CI and Qodo had reviewed it. That tied the doc to the PR's review loop. Qodo reviewed the doc itself and raised findings about it (#46). Each regeneration was a push, which triggered another Qodo re-review and made the doc stale again (#34 needed three regenerations). Closing a finding rewrote Qodo's comment, which the doc copies. A restored SHA got no re-review at all. #35 merged without its doc and #36 added it after the merge, and that worked, because the generator reads everything from the PR. This PR makes that the process: a PR merges with no doc, and its doc comes afterwards in a docs PR, recording the final state.

## How

_From the PR description (author-written)._

- `scripts/check-delivery.sh` (CI mode) no longer looks for the PR's own doc. It lists the PR's changes: HEAD (in CI, the merge commit) against `BASE_SHA`, which defaults to `HEAD^1`, the merge commit's base parent.
  - If any changed file is outside `deliveries/`, it is a code PR. The check prints a notice that the doc comes in a docs PR after the merge, and passes. It gives no warning and no error.
  - Otherwise it is a docs PR. For each `deliveries/<name>.md` the PR adds or changes (not `TEMPLATE.md`, and not files in screenshot directories), the doc's last metadata line must name the merged head (`head=`), and the doc's recorded `content=` must equal that head's content digest. CI's clone is shallow, so a head that isn't in the clone is fetched from `origin` (`git fetch --depth=1`). A head that can't be fetched fails the check.
  - `qodo-open` is now evidence, not a gate: 0 passes, and `none`, `other`, `unknown` or a count above 0 gives a `::warning` and still passes. A missing `qodo-open` still fails. The `qodo-findings` status is the merge gate (rule 9).
  - The delivery window cutoff (2026-12-12 23:00 UTC) and `--window` / `--digest` are unchanged.
- `scripts/generate-delivery.sh`:
  - It refuses a PR whose `state` is not `MERGED`.
  - It cites the latest passing Check site run on the merged content, instead of the earliest. The earliest was chosen only so that a pre-merge amend wouldn't move the evidence.
  - It writes `head=<merged head>` into the metadata line: `content=… head=… homepage=… qodo-open=…`.
  - The merge-base homepage comparison (rule 7) and the Qodo edit-history reading (cleared findings) are unchanged, and they work on a merged PR.
- `AGENTS.md`: rules 6, 7 and 9, the Verify comment for `--check` and the Workflow section now describe the post-merge process.
- The delivery-doc skill runs Qodo triage before the merge and generates the doc after it, in a docs PR that changes only `deliveries/`.
- The PR template says the doc is generated after the merge, in a separate docs PR.
- The delivery-doc CI job drops the env vars `check-delivery.sh` no longer reads.
- `generate-delivery.sh` fetches a CI run's missing commit (`--fetch REMOTE`, default `upstream`) and stops if a newer run can't be fetched (tests `fet`, `fet2`).
- `generate-delivery.sh` ignores Check site runs created after the PR merged, which belong to a later PR on a reused branch (tests `reu`, `mrg`).
- `generate-delivery.sh` skips headings inside ``` and ~~~ fences (`ac.` traps).
- `agent-run.sh`'s done comment says the owner merges, then runs the skill.

## What

_From the PR description (author-written)._

- After a PR merges, its delivery doc is generated from the merged PR and added in a separate docs PR. One docs PR can carry several docs, and a docs PR needs no doc of its own.
- On a code PR, CI's delivery-doc job is green and asks for no doc.
- On a docs PR, CI checks that each doc matches the content of the merged head it names.
- The doc records the merged head, the final passing CI run, and Qodo's final review, including the findings Qodo cleared.
- New and updated cases in `scripts/test-delivery.sh`, which CI already runs in the "Test delivery scripts" step:
  - `a2`: the doc names the merged head and passes.
  - `code`: a code PR passes without a warning, even if it carries a stale doc.
  - `shot`: a screenshot- or template-only docs PR passes with no doc read.
  - `d`/`d2`: a doc whose head has other content fails, and passes once regenerated.
  - `nohd`: a doc with no `head=` fails.
  - `unk`: an unknown base fails.
  - `ftch`: in a shallow clone the head is fetched from origin, and a head origin lacks fails.
  - `fin`: the latest passing run is cited and a later failing one isn't.
  - `opn`: an open PR is refused and no doc is written.
  - `qo*`: non-zero, `none`, `other` and `unknown` warn and pass; a missing Qodo state still fails.
  - The fixed-point test `fp` covered pre-merge amends, which no longer happen, so it is replaced by `fin`.
- `.claude/skills/delivery-doc/SKILL.md`: runs Qodo triage before the merge, and generates the doc after it in a docs PR.
- `.github/pull_request_template.md`: says the doc is generated after the merge, in a separate docs PR.
- `.github/workflows/check-site.yml`: the delivery-doc job drops the env vars `check-delivery.sh` no longer reads.
- `AGENTS.md`: rules 6, 7 and 9, the Verify comment for `--check`, and the Workflow section describe the post-merge process.
- `scripts/agent-run.sh`: the done comment says the owner merges, then runs the skill.
- `scripts/check-delivery.sh`: in CI, a code PR passes with no doc; a docs PR checks each doc against its merged head.
- `scripts/generate-delivery.sh`: fetches a CI run's missing commit (`--fetch REMOTE`) and stops if a newer run can't be fetched; skips headings inside ``` and ~~~ fences (`ac.` traps); ignores runs created after `mergedAt` (tests `reu`, `mrg`); tests `fet`, `fet2`.
- `scripts/test-delivery.sh`: the new and updated cases, including `fet`, `fet2`, `reu`, `mrg` and the `ac.` fence traps (a backtick info string and a 4-space-indented fence line).

## Limitations

_From the PR description (author-written)._

- The hand-added Qodo dashboard rules about delivery docs and `qodo-open` still describe the old process; the owner updates them in app.qodo.ai.
- **Not tested in CI:**
  - The fetch of the merged head runs against GitHub only in CI on a real docs PR. The test fetches from a local `file://` origin with `uploadpack.allowAnySHA1InWant`. GitHub serves reachable SHAs to anonymous fetches of a public repo, but that is not exercised before the first docs PR.
  - CI checks that a doc matches the head it names. It doesn't check that the head is the merged head of the PR the doc names, because that needs the GitHub API. The generator reads the head from `gh pr view` and refuses an unmerged PR.
  - The real `gh pr view --json state` response (`MERGED`) is stubbed in the tests, like the generator's other `gh` calls.
- Existing docs on `main` have no `head=`. They are never changed (rule 6), and a docs PR that changed one would now fail with "no merged head".
- A docs PR that deletes a doc isn't flagged: the deleted doc isn't in HEAD, so nothing is checked.
